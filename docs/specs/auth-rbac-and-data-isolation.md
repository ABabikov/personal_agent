# Спецификация: авторизация, ролевая модель и изоляция данных

**Версия:** 0.5  
**Статус:** черновик для реализации  
**Связанные документы:** [docs/architecture.md](../architecture.md), миграции Supabase (`001_*`, `002_dev_anon_*`, `005_swim_block_catalog.sql`)

---

## 1. Цели

1. **Идентификация пользователя** — каждый запрос к персональным данным выполняется от имени ровно одного субъекта (`user`), без «общих» записей тренировок/чата/профиля между разными людьми.
2. **Авторизация** — явные роли и правила, кто что может читать и менять (в т.ч. общий каталог vs персональные сущности).
3. **Общие (неперсональные) данные** — единый источник правды для примеров программ, справочника упражнений, шаблонов серий плавания и т.п.; они **не** привязаны к конкретному пользователю, но **доступны всем** в режиме чтения (и ограниченно — копирования в свой контекст).
4. **Совместимость с текущим кодом** — поэтапный переход от режима «один пароль на сайт + `WORKOUT_USER_ID` / dev RLS» к Supabase Auth и политикам по `auth.uid()`.
5. **Идентификация без почты и телефона** — основной внешний ключ: **Telegram user id** (`telegram_id`); **email и телефон не** используются для входа, профиля и хранения в наших таблицах; не заставлять пользователя придумывать логин (см. 3.2, 3.5).

### 1.1 Вне scope: бизнес-логика фич не меняется

Эта спека **не** планирует и **не** требует пересмотра или переписывания доменной логики:

- **тренировки** — журнал, расчёты (тоннаж, метраж, калории и т.п.), планы, плавание, каталоги блоков как продуктовые правила;
- **финансы** — счета, категории, импорт выписок, идемпотентность, отчёты;
- **питание** — планы, КБЖУ, рецепты, списки покупок;
- **импорт с устройств** — форматы, парсинг, дедупликация, привязка к тренировкам.

На будущее под эту спеку входят только слой **«кто пользователь / сессия»**, привязка **`user_id`**, **RLS и проверки доступа в API/агенте**. Поведение и алгоритмы перечисленных модулей остаются **как в текущем коде**, если отдельным ТЗ не решено иное.

## 2. Термины

| Термин | Значение |
|--------|----------|
| **Аутентификация** | доказать, кто ты (сессия JWT Supabase, при необходимости — доп. слой `SITE_PASSWORD` для закрытой инсталляции). |
| **Авторизация** | что тебе разрешено (роль + RLS + проверки в API/агенте). |
| **`auth.users`** | учётные записи Supabase Auth (`id` = UUID субъекта в JWT). |
| **`public.users`** | субъект для RLS: UUID, **`telegram_id`** (основная привязка к аккаунту в TG), служебные поля; **без** email/телефона в таблице; антропометрия — по политике 3.5. |
| **Персональные данные** | в юридическом смысле (PII + чувствительные) — см. PII и «чувствительные не-PII». В смысле **изоляции по аккаунту** ниже по тексту: «данные владельца» = строки с `user_id` → `public.users.id` (не путать с PII). |
| **Каталог / shared** | данные без владельца или с `user_id IS NULL` (системные шаблоны); не содержат PII чужих пользователей. |
| **PII (избегаем в продукте)** | **email, телефон**, почтовый адрес, ФИО как обязательные поля — **не** собираем и **не** кладём в `public.*`. **`telegram_id` — разрешён** и считается выбранным способом идентификации пользователя (как в текущей схеме БД). |
| **Чувствительные не-PII** | данные о теле/здоровье/финансах (вес, рост, диагнозы, суммы) — отдельный юридический/продуктовый класс; по политике продукта могут не храниться, храниться только локально или шифроваться (не смешивать с «логином»). |

## 3. Модель идентичности

### 3.0 Как сейчас (факт по коду) — не целевой прод

- **Нет** регистрации с логином/паролем, который пользователь придумывает сам.
- Общий **пароль сайта** (`SITE_PASSWORD`) + cookie-сессия — это защита инстанса, а не учётная запись человека.
- Идентификатор данных — UUID строки в `public.users`: либо из env (`WORKOUT_USER_ID` / `NEXT_PUBLIC_WORKOUT_USER_ID`), либо **автосоздание** пустой строки при первом обращении (`insert` с пустыми полями). Пользователь **ничего не вводит** для «создания аккаунта».
- Поля вроде `weight`, `height`, `age`, `gender` в таблице `users` — **чувствительные**; по желанию продукта их можно вынести из `public.users` (см. 3.5). **`telegram_id` остаётся** как согласованный внешний идентификатор (не избегаем).

### 3.1 Источник истины для «текущего пользователя»

- **Целевой режим (прод):** `auth.uid()` из JWT Supabase (cookie / заголовок `Authorization` в API, серверные route handlers и Edge при необходимости).
- **Связка Auth ↔ приложение:** при первом успешном входе создаётся (или догружается) строка в `public.users` с `id = auth.uid()` **или** отдельная колонка `public.users.auth_user_id uuid unique references auth.users(id)` — выбор фиксируется в миграции; в спеке важно правило: **один субъект входа ↔ один ряд приложения**.

### 3.2 Регистрация и вход — Telegram-first, без почты и телефона

Пользователь **не** придумывает логин/пароль приложения. **Email и телефон не участвуют** в регистрации и входе (ни magic link, ни SMS, ни обязательные поля профиля).

| Схема | Назначение | `public.users` |
|-------|------------|----------------|
| **Telegram Mini App / Login Widget** | основной поток: подписанный `initData` или аналог на сервере → сессия (JWT / cookie) | `telegram_id` **храним** (bigint, unique), связь с `auth.uid()` или `id` по выбранной миграции |
| **Anonymous / device (опционально)** | веб без TG: временный аккаунт до привязки к TG | UUID, `telegram_id` null до привязки |
| **Passkeys (опционально)** | доп. фактор для веба, **не** замена `telegram_id` как источника правды для TG-пользователя | по решению продукта |

**Вне scope продукта:** magic link, Sign in with Email, телефонный OTP, сбор email «на всякий случай».

### 3.3 Telegram Mini App

- После **проверки подписи** `initData` на сервере извлекается `user.id` → это и есть стабильный **`telegram_id`** для строки `public.users` и для RLS-изоляции данных.
- Клиенту не доверяем «голый» id без проверки подписи бот-токеном.
- Техническая реализация — `docs/deploy/telegram-mini-app.md` и обмен на сессию Supabase **без** проброса email/телефона из TG в наши таблицы (в API Telegram они для бота обычно недоступны — не собирать с других источников).

### 3.4 Опциональный «замок на сайт»

- Переменные `SITE_PASSWORD` / `SITE_AUTH_SECRET` остаются **периметром** (например, личный инстанс), но **не** заменяют привязку данных к пользователю: после прохода замка всё равно нужна сессия Supabase (или явный single-tenant режим с одним `auth.uid()` — см. раздел 8).

### 3.5 Данные: что избегаем, что оставляем

**Инвариант продукта (аутентификация и контакты):**

- **Не используем:** email, телефон, magic link, SMS — ни для входа, ни как обязательные поля в UI/БД.
- **Используем:** **`telegram_id`** в `public.users` как основной внешний идентификатор человека в экосистеме Telegram.

**Прочее:**

- **Антропометрия** (`weight`, `height`, `age`, `gender`, …) — отдельное продуктовое решение (оставить в `users` / вынести / клиент-only); к почте и телефону не относится.
- **Логи:** не писать в логи email/телефон даже если когда-то появятся в запросах; `telegram_id` — только при необходимости отладки и с ограничением доступа.
- **`auth.users`:** не включать провайдеры, требующие email, как основной путь; предпочтительны anonymous JWT + серверная выдача сессии после проверки `initData`, либо официальный поток Telegram ↔ Supabase без дублирования email в `public.*`.

## 4. Роли (RBAC)

Минимальный набор на первый этап:

| Роль | Код | Назначение |
|------|-----|------------|
| Пользователь | `user` | полный CRUD только по своим персональным данным; чтение каталога. |
| Администратор каталога | `catalog_admin` | CRUD по строкам каталога (`user_id is null` и/или таблицы только-каталог); без доступа к чужим персональным данным. |
| Супер-админ (опционально) | `super_admin` | обход только для саппорта/миграций; по умолчанию **выключен** в проде; любое использование логируется. |

Хранение ролей (один из вариантов — зафиксировать при реализации):

- **A:** `public.users.role text` + enum в приложении;  
- **B:** `user_roles(user_id, role)` many-to-many;  
- **C:** кастомные claims в JWT (редко меняется) + зеркало в БД для RLS.

**Правило:** бизнес-фичи не проверяют роль в 20 местах — только модуль `lib/auth/permissions.ts` (или аналог) + RLS.

## 5. Классификация данных

### 5.1 Персональные сущности (всегда `user_id NOT NULL` и равен владельцу)

Примеры по проекту: `workouts`, `workout_plans`, `gym_exercises` (если привязаны к журналу пользователя), `chat_messages`, `user_context`, транзакции расходов, пользовательские копии планов питания и т.д.

**Инвариант:** любой `SELECT`/`INSERT`/`UPDATE`/`DELETE` в проде — только если `user_id = auth.uid()` (или согласованный FK от строки, у которой корневой `user_id` совпадает).

### 5.2 Каталог / общие данные

Признаки:

- Не содержат данных о конкретном человеке (имя, вес, история).
- Одинаковы для всех; версионируются при необходимости (`version`, `active`, `slug`).

Примеры: системные строки в `swim_block_template` с `user_id IS NULL` (уже заложено в миграции), справочник упражнений, демо-планы тренировок, сиды рецептов без привязки к аккаунту.

**Инвариант чтения:** `authenticated` может `SELECT`.  
**Инвариант записи:** только `catalog_admin` / сервисная роль (seed, CI).

### 5.3 Гибрид: «шаблон из каталога → у пользователя»

- Пользователь **не** редактирует системный шаблон.
- Операции «добавить в мой план» создают **новую** строку с `user_id = auth.uid()` и ссылкой `source_template_id` / `copied_from` (опциональная колонка). Так персональные данные остаются изолированными, а происхождение от каталога прослеживается.

## 6. Политики RLS (требования уровня прод)

Заменить dev-политики вида `using (true)` на:

| Таблица / класс | SELECT | INSERT | UPDATE | DELETE |
|-----------------|--------|--------|--------|--------|
| Персональные | свой `user_id` | только свой `user_id` | только свой | только свой |
| Каталог | все `authenticated` | роль админа / service | админ / service | админ / service |
| `public.users` (профиль) | своя строка | своя (on signup) | своя | по политике продукта (часто запрет delete) |

**Чат и агент:** `chat_messages`, `user_context` — строго по `user_id`; инструменты агента на сервере вызывают только функции, внутри которых `userId` берётся из сессии, **не** из тела запроса клиента (клиент может прислать подсказку `conversationId`, но не «чужой» `user_id`).

## 7. API и UI

- **Middleware:** после внедрения Supabase Auth — редирект неавторизованных на `/login` (или страница логина провайдера); при сохранении `SITE_PASSWORD` — последовательность: замок → затем Supabase session.
- **`/api/*`:** в каждом handler первый шаг — `getSession()` / `getUser()`; отсутствие сессии → `401`.
- **Клиентский `getWorkoutUserId()`:** эволюция в `getCurrentUserId()` из сессии Supabase; `NEXT_PUBLIC_WORKOUT_USER_ID` только для локальной отладки с явным предупреждением в доке.

## 8. Миграция существующих данных (ничего не теряем)

Принцип: **данные в таблицах фич не удаляются и не «обнуляются»** из‑за смены входа. Меняется только способ привязки сессии к уже существующим строкам (`user_id` / FK). Каталог (`user_id is null` и пр.) **не трогается**.

### 8.1 Перед любыми изменениями

1. **Полный бэкап** Postgres (снапшот / `pg_dump`), хранение вне прод-сервера.
2. **Заморозка схемы** на время cutover: нет параллельных ручных `DELETE`/реструктуризаций без чеклиста.
3. **Инвентаризация:** по каждой таблице с `user_id` или FK на `users` — зафиксировать `count(*)`, `min(created_at)`, `max(created_at)` (или аналог) в артефакт миграции для сравнения «до/после».

### 8.2 Типичные сценарии (выбор при реализации)

| Сценарий | Суть | Риск потери |
|----------|------|-------------|
| **A. Один «наследуемый» `public.users.id`** (один UUID на всё, как сейчас часто с env) | Новый `auth.users.id` **приравнивают** к этому же UUID (если Supabase позволяет создать пользователя с заданным id — уточнить в доке / через admin API) **или** вводится таблица соответствия `legacy_user_id → auth_user_id` и **один раз** обновляются FK во всех зависимых таблицах транзакцией. | Низкий при транзакции + бэкапе |
| **B. Несколько строк `users` с разными `telegram_id`** | Уже есть естественный ключ: маппинг **по `telegram_id`** при первом входе в TG; строка `public.users` остаётся той же, меняется только появление сессии `auth`. | Низкий |
| **C. Анонимные `users` без TG** | После входа через TG — `UPDATE public.users SET telegram_id = …` для той же строки **или** merge по правилам саппорта (явный сценарий, не автомат без UX). | Средний без UX-слияния |

**Инвариант:** все строки `workouts`, `workout_plans`, `chat_messages`, `expense_*`, и т.д. остаются с **тем же смыслом владельца**; допускается только смена UUID в FK **если** выполнен полный проход всех FK в одной транзакции с проверкой ссылочной целостности.

### 8.3 Порядок работ (черновик этапов)

1. Staging с копией прод-данных; прогон миграции скриптом/SQL.
2. Сравнение **числа строк** по каждой затронутой таблице до/после; `SELECT` выборочных связей (например, `workouts.user_id` ∈ `users.id`).
3. Включение RLS **после** того, как сессии выдаются с корректным `auth.uid()` для тех же людей.
4. Прод: то же в окно обслуживания или blue/green с read-only на время миграции (по риску).
5. Откат: восстановление из бэкапа **или** откат транзакции, если миграция не закоммичена.

### 8.4 Что точно не пересоздаём с нуля

- История тренировок, финансов, питания (если уже в БД), импорты, чат, `user_context` — **только перепривязка идентичности**, не пересчёт доменных полей и не «чистый лист».

### 8.5 Критерий «ничего не потерялось»

- Совпадение контрольных **count** по всем таблицам с `user_id` (и дочерним через FK) до и после.
- Выборочная сверка N записей (хэш или `id` списков) по критичным таблицам.
- Smoke-тест UI: тот же пользователь видит те же тренировки/суммы после входа.

### 8.6 Инфраструктура входа (после сохранности данных)

- Подключить Supabase Auth и выдачу сессий (TG / см. §3).
- Сузить `002_dev_anon_*` на проде только когда §8.5 выполнен на staging.
- Задокументировать переменные в `docs/deploy/` (замок инстанса + Auth).

## 9. Критерии приёмки (кратко)

- Два разных пользователя после входа **никогда** не видят чужие тренировки, чат, профиль, расходы, контекст агента (ни через UI, ни через tools при корректной конфигурации ключей).
- Каталог (упражнения, примеры, системные блоки плавания) **виден** обоим; изменение каталога без роли админа **невозможно**.
- Попытка подставить чужой `user_id` в REST или tool-call **не** меняет данные другого пользователя (сервер игнорирует или подставляет только `auth.uid()`).
- В UI **нет** обязательных полей email и телефона; вход не завязан на них.
- После миграции идентичности **совпадают контрольные count** по таблицам с `user_id` (см. §8.5).

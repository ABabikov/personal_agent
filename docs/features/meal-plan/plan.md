# Meal Plan & Shopping — план реализации

## Принятые продуктовые решения (из обсуждения)

1. **План по дням** — не только «набор блюд на неделю», а привязка к **датам** (день N: завтрак / обед / ужин / перекусы — состав слотов можно упростить в MVP до «слоты в день» или 3–4 приёма).
2. **Порции** — для каждой ячейки плана явно задаётся **количество порций** рецепта (дробные допустимы при необходимости, по умолчанию целые).
3. **КБЖУ-коридор** — задаётся **нижняя и верхняя граница** по ккал (и опционально по Б/Ж/У). **Весь коридор чуть ниже** ручной номинальной «проги»: при одной и той же «проге» верхняя граница коридора не превышает прогу (или прога − фиксированный/процентный зазор — константа в настройках). Так проще по умолчанию не «переесть» номинал.
4. **Дефицит / профицит** — показывать расчёт: **оценка расхода** (база TDEE из профиля при наличии + **средний расход по тренировкам** за выбранный период + **импорт с часов** когда будет) минус **сумма запланированных ккал** (среднее или по дням). Пока нет часов: явная пометка «без данных часов» и опциональный ручной коэффициент.
5. **Рецепты** — **поиск в интернете**, отбор **простых и вкусных**, с нормализованными КБЖУ (парсинг страницы, таблица NutriCalc, или оценка + ручная правка). Кеширование URL, дедуп, легальность (robots, ToS источника).
6. **Список покупок** — **один общий** на период плана. **Интеграции магазинов / автозаказ** — отдельная фаза после стабильного списка и модели данных.

## Модель данных (черновик)

### `meal_targets` (или настройки пользователя)

- Номинальная «прога»: `target_kcal`, опционально `target_protein_g`, …
- Коридор: `kcal_low`, `kcal_high` (вычисляются из проги и правила «весь коридор ниже»), либо `corridor_pct` + `offset_below_target_kcal`.
- Связь с профилем: `user_id`, ссылка на TDEE из `users` / профиля.

### `meal_plan_day`

- `user_id`, `date` (локальная дата)
- Опционально `slot` (`breakfast` | `lunch` | `dinner` | `snack` | произвольный порядок)

### `meal_plan_item`

- `day_id` / (`user_id` + `date` + `slot`)
- `recipe_id` (внешний или внутренний)
- `portions` (numeric)

### `recipes` (каталог + импорт из сети)

- `source_url`, `title`, `body` или шаги
- `macros_per_serving` (ккал, Б, Ж, У) — обязательно после импорта; флаг `verified_by_user`
- `effort_score` / теги «незапарно» (ручной или LLM)

### `pantry_staples` (база дома)

- Список строк + опционально синонимы для матчинга к ингредиентам.

### `shopping_list_snapshot` (опционально позже)

- Агрегат на период, версия, для будущих интеграций с магазинами.

## Интеграция с чатом (агент)

- **Тулы:** `get_meal_plan_state`, `set_meal_plan_state` в `src/lib/agent/tools/meal_plan.ts`, зарегистрированы в `AGENT_TOOLS`.
- **Контекст сервера:** `ToolContext.mealPlanClient` — снимок после разбора тела запроса.
- **Тело `POST /api/chat`:** опциональное поле **`mealPlan`**: JSON `{ targets, staples, plan }` (как возвращает `readMealPlanSnapshotForAgent()` на клиенте). Разбор: `safeParseClientMealPlanPayload` в `mealPlanMerge.ts`. Если поле отсутствует или битое — тулы питания сообщают, что снимка нет.
- **Клиент:** `global-chat.tsx` и `chat/page.tsx` при каждом сообщении прикладывают `mealPlan`, если удалось прочитать `localStorage`. После ответа ассистента вызывается `applyMealPlanFromChatSteps` — при успешном `set_meal_plan_state` пишется `writeMealPlanSnapshotFromAgent` и шлётся событие `personal-agent-meal-plan-updated` (страница `/meal-plan` подписана и перезагружает стейт).
- **Правила для модели:** в `prompts/system.ts` — питание по смыслу как запись в БД: сначала явное согласие пользователя, затем `set_meal_plan_state`. `recipeId` в `plan` только из каталога сидов (список в ответе `get_meal_plan_state.knownRecipeIds`).

## Phases

### Phase 0: Документация и согласование правил коридора

- [ ] Зафиксировать формулу: как именно «коридор чуть ниже проги» считается из UI-полей (одна страница «настройки питания»).
- [ ] Зафиксировать источник «средний расход по тренировкам» (SQL/агрегация из существующих таблиц, период скользящий 7/14/28 дней).

### Phase 1: План по дням + порции + коридор + баланс (без веб-рецептов)

- [ ] UI: календарь/список дней, слоты, выбор рецепта из **локального каталога** (как сейчас в прототипе или из БД).
- [ ] Ввод порций на ячейку; суммирование КБЖУ по дню и по неделе.
- [ ] Подсветка дней: в коридоре / ниже / выше.
- [ ] Блок «баланс»: TDEE (из профиля) + средние калории тренировок за период − план приёма (по дням или среднее).
- [ ] Общий список покупок с агрегацией и базой дома (как в прототипе, но от **плана по дням**).

### Phase 2: Рецепты из интернета

- [ ] Интеграция с существующим `web_search` агента или отдельный серверный поиск + whitelist доменов.
- [ ] Пайплайн: URL → извлечение текста → парсинг ингредиентов / КБЖУ (эвристики + ручное подтверждение).
- [ ] Кеш рецептов в БД, дедуп по URL.
- [ ] Фильтр «незапарно» (ключевые слова, время ≤ N мин, число ингредиентов ≤ M).

### Phase 3: Часы и точный расход

- [ ] Подключить импорт активности с часов (общий трек с `workout-tracker` / Huawei и т.д.).
- [ ] Включить суточный/недельный расход в формулу дефицита/профицита.

### Phase 4: Магазины и автозаказ

- [ ] Экспорт списка в форматы партнёров; при наличии API — подтягивание цен/наличия.
- [ ] Автозаказ (после явного согласия, лимиты, выбор магазина).

## Technical Decisions

| Решение | Выбор | Обоснование |
|---------|--------|----------------|
| Хранение плана MVP | Сначала расширить текущий клиентский стейт или сразу Supabase | Supabase даёт мульти-девайс и основу под интеграции; прототип можно мигрировать |
| Коридор ниже проги | Конфиг: `high = target - delta_kcal`, `low = high - width` (пример; финальная формула в Phase 0) | Явное правило, предсказуемый UI |
| Средний расход тренировок | Агрегат `calories_estimated` (и позже плавание) за скользящее окно | Данные уже пишутся для силовых |
| Веб-рецепты | Серверный fetch + кеш, не голый клиент к произвольным URL | CORS, безопасность, ToS |
| Питание + агент | Снимок в `POST /api/chat.mealPlan`, запись через `set_meal_plan_state` → клиент пишет `localStorage` | Пока нет Supabase для питания; единый контракт до миграции в БД |

## Dependencies

- **Internal:** профиль (`/profile`), тренировки и калории, будущий импорт часов.
- **External:** поиск/сайты рецептов; позже — API магазинов.

## Risks

| Риск | Митигация |
|------|-----------|
| Неточные КБЖУ с сайтов | Флаг «не проверено», ручная правка, минимальный доверенный каталог |
| Юридические ограничения на парсинг | Whitelist, ссылки на первоисточник, не хранить длинные копипасты без разрешения |
| Перегруз UI при плане по дням | Начать с недели и 3–4 слотов, сохранять в БД |

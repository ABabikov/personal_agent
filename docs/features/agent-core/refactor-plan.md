# Agent Core — план рефакторинга «настоящий тренер»

> Составлен 2026-06-04 на основе [audit.md](./audit.md). Цель: чат должен работать как настоящий
> персональный тренер — проактивный, помнящий, методически грамотный, связывающий питание и нагрузку.
> Принцип проекта сохраняем: **dual-mode** — вся новая логика в `lib/features/*`/`lib/db/*`, доступна
> и UI, и агенту. Каждая фаза — отдельный согласуемый шаг; код пишем только после «да».

Номера `#N` ссылаются на находки аудита.

---

## Фаза 0 — «Разлепить» обвязку (XS–S, максимум эффекта) ✅ ВЫПОЛНЕНО 2026-06-04

Чинит ощущение «дёшево и коротко» без изменения бизнес-логики и без выбора модели.

> **Результат:** дефолт `max_tokens` 1024 → 4096 (`models.ts`); `temperature` вынесена в
> `getAgentTemperature()` (дефолт 0.4, `OPENROUTER_TEMPERATURE`); `runAgent` отдаёт `finalModel` +
> `usedFallback`, в UI чата всегда виден бейдж модели (янтарный при фоллбеке); добавлен health-check
> `npm run diagnose:llm`. Диагностика на 2026-06-04: основная модель `claude-sonnet-4` отвечает,
> эмбеддинги живы, баланс есть — молчаливого даунгрейда сейчас нет. Главным тормозом был лимит 1024.

1. **Лимит токенов (#1).** Поднять рабочий потолок ответа до 2048–4096
   (`OPENROUTER_MAX_COMPLETION_TOKENS` в `.env`; код в `models.ts` уже поддерживает). Проверить, что
   тренерские ответы перестали обрываться (`finish_reason`).
2. **Видимость модели (#2).** Вынести `modelUsed` и факт даунгрейда в шапку ответа (бейдж), а не в
   свёрнутый блок. Логировать `attempts` явно. Опционально — баннер «работаю на резервной модели».
3. **Диагностика среды (#2,#3).** Разовый health-check: баланс OpenRouter, валидность id основной
   модели, реально ли отрабатывают эмбеддинги. Зафиксировать результат.
4. **temperature (#9).** Вынести в конфиг; для коуч-диалога чуть поднять (0.4–0.6), для расчётных
   тулов оставить низкой.

**Критерий готовности:** ответы не обрезаются; в UI видно, какая модель ответила; подтверждено, что
эмбеддинги/память живы.

## Фаза 1 — Память, которая помнит (#3, #4)

Без памяти «тренер» невозможен.

5. **pgvector-RPC.** Создать `match_chat_messages(p_user_id, p_embedding, p_limit, p_exclude_conv)` и
   `match_user_context(...)`, заменить брутфорс-фоллбек в `recall.ts` на RPC (фоллбек оставить как
   страховку). Миграция `015_*`.
6. **Деградация без эмбеддингов.** Если `embedText` упал — не терять память полностью: отдавать
   последние N фактов и недавние сообщения по времени (частично уже есть в `sessionSnapshot`).
7. **Авто-факты.** После каждых K сообщений — фоновый вызов LLM «вытащи устойчивые факты»
   (цели, травмы, предпочтения, PR) → `remember_fact` (без подтверждения для фактов о пользователе,
   в отличие от записи тренировок). Дедуп по ключу.
8. **Окно контекста (#4).** Ограничить историю разговора (последние N сообщений + суммаризация
   «хвоста»); ужимать JSON-выхлопы тулов перед переподачей в цикл.

**Критерий:** агент в новом разговоре корректно ссылается на цели/факты и прошлые тренировки.

## Фаза 2 — Методика тренировок (#6)

«Тренерский мозг» для зала (у плавания методический блок уже есть).

9. **Прогрессия 2.0.** Заменить наивный `+1 повтор` на нормальную модель в
   `lib/features/workouts/`: целевые диапазоны повторов под цель (сила/гипертрофия/выносливость),
   учёт RPE/запаса, авто-deload при стагнации/откате, разумный шаг веса по упражнению.
   Подключить и в UI-кнопку прогрессии, и в `suggest_next_gym_sets`.
10. **Методический блок зала в промпте.** По образцу `SWIM_GENERATION_COACH_PROMPT_BLOCK` — выверенный
    текст про периодизацию, баланс групп мышц, восстановление; инжектить в `system.ts`.
11. **Сценарий «составь тренировку» 2.0.** Учитывать недавнюю нагрузку, дисбаланс, цель и
    восстановление, а не только «как было в прошлый раз для этого дня недели».

**Критерий:** рекомендации по весам/повторам методически обоснованы и объясняются.

## Фаза 3 — Цели и сверка прогресса (#7)

12. **Сущность «цель».** Таблица `goals` (тип, целевые метрики, дедлайн, статус) + миграция + типы +
    тулы `get_goals`/`set_goal`/`update_goal_progress`. UI — карточка цели в профиле/на главной.
13. **Сверка с целью.** Агент при анализе соотносит фактический прогресс с целью (опережение/отставание)
    и корректирует рекомендации.

**Критерий:** на вопрос «как я иду к цели?» агент даёт привязанный к цифрам и срокам ответ.

## Фаза 4 — Проактивность (#5)

14. **Расширить `sessionSnapshot`:** тренды (тоннаж/веса/частота), пропуски относительно плана,
    дисбаланс зал/плавание, дефицит/профицит ккал vs цель.
15. **Проактивный промпт.** Инструкция: в начале диалога/по запросу «как дела» — сам подмечай 1–3
    наблюдения и давай конкретную рекомендацию, без воды.
16. **(Опц.) Дайджест тренера** — кнопка/виджет «разбор недели» поверх той же логики.

**Критерий:** агент сам поднимает важное (пропуски, стагнация), а не только отвечает на прямой вопрос.

---

## Фаза 5 — Питание × тренировки (#7, межфичевое)

17. **Связать КБЖУ/калории с нагрузкой и целью:** дефицит/профицит в контексте недельного объёма и
    цели; учёт сожжённых на тренировке калорий. Логика — общая для `/meal-plan` и агента.
18. **Единый снимок «день»:** тренировка + питание + восстановление в одном контексте для агента.

**Критерий:** агент рассуждает о питании в связке с нагрузкой и целью, а не изолированно.

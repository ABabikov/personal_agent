# ТЗ: каталог бассейновых заданий по целям и сборка тренировки из заготовок

## 1. Цель

Сделать **каталог типовых блоков заданий**, разложенный по **целям тренировки** (техника, скорость, аэробика, смешанная и т.д.), а **конкретный объём одной сессии** получать **сборкой** из этих заготовок с **лёгкой подгонкой метража** (шаг 25 м, добор/срез без «левых» отдельных 50 м без контекста).

Каталог хранит не готовые «тренировки на N метров», а **переиспользуемые куски** + правила, как их масштабировать под запланированный объём.

---

## 2. Принципы

| Принцип | Формулировка |
|---------|----------------|
| Цели | Пользователь выбирает **цель** (или фокус из того же семейства); от неё зависит приоритет типов блоков. |
| Объём сессии | Задаётся отдельно на конкретную тренировку (например 2400 м); каталог **не** фиксирует один общий объём «навсегда». |
| Сборка | Алгоритм набирает цепочку блоков по фазам (разминка / основа / заминка), подбирая шаблоны по тегам цели. |
| Подгонка | Если сумма не совпадает с целевым объёмом — корректировать в пределах `min_m`/`max_m` и режима масштабирования; мелкий хвост **приклеивать** к последнему осмысленному блоку, а не выносить отдельной карточкой «50 м контроль». |
| Разнообразие | Не подставлять подряд один и тот же `slug` блока без необходимости. |

---

## 3. Модель данных (Supabase)

### 3.1. Цели

На первом этапе допустимо **не заводить таблицу**: кодовые значения enum + описание в UI.

Примеры кодов: `technique`, `speed`, `aerobic`, `mixed`, `recovery`.

При необходимости таблица `swim_goal`: `code`, `name_ru`, `description`, опционально `chunk_priority` (JSON).

### 3.2. Шаблон блока `swim_block_template`

| Поле | Тип | Назначение |
|------|-----|------------|
| `id` | uuid | PK |
| `user_id` | uuid | Владелец; для системных заготовок — null или выделенный системный пользователь (решить в миграции). |
| `slug` | text | Уникальный ключ (`pyramid_classic`, `5x100_cruise`, …). |
| `goal_tags` | text[] | Для каких целей подходит. |
| `phase` | enum | `warmup` \| `main` \| `cooldown` |
| `nominal_distance_m` | int | Ориентировочный метраж блока. |
| `min_m` | int | Нижняя граница осмысленного масштаба. |
| `max_m` | int | Верхняя граница. |
| `scale_mode` | text | Логика подгонки: `fixed`, `stretch_tail`, `merge_remainder_into_previous`, … (уточняется при реализации). |
| `body_text` | text | Текст задания в принятом формате (многострочный). |
| `source` | text | `own` \| `curated` \| `generator_seed` |
| `source_note` | text | Кратко откуда идея (без длинных цитат чужих текстов). |
| `active` | boolean | Мягкое отключение блока. |
| `created_at` / `updated_at` | timestamptz | Аудит |

Индексы: по `(phase)`, по `goal_tags` (GIN), по `(user_id)` если блоки персональные.

**RLS:** по аналогии с `workouts` — пользователь видит свои блоки + опционально глобальные системные.

## 4. Откуда брать тексты кусков

| Источник | Действие |
|----------|-----------|
| Своя история | Разбор сохранённых тренировок (CSV/Supabase): выделить повторяющиеся серии → завести блоки с `source = own`. |
| Текущий генератор (`generatePlan.ts`) | Вынести устойчивые формулировки в seed-записи `generator_seed`; генератор постепенно перевести на «выбор из каталога + подгон». |
| Внешние подборки (USMS и др.) | Только **пересказ структуры своими словами**, короткая пометка в `source_note`; не хранить длинные копипасты без проверки условий использования сайта. |
| Чат агента | Позже: действие «сохранить как блок» → черновик → после подтверждения в каталог. |

---

## 5. Алгоритм сборки тренировки

**Вход:** код цели, целевой объём сессии `V` (м), опционально текст фокуса.

**Шаги:**

1. Разбить `V` по фазам (как сейчас на клиенте: доля разминки, основы, заминки — возможно зависеть от цели).
2. Для каждой фазы выбрать кандидатов из `swim_block_template`: фильтр по `phase`, пересечение `goal_tags` с целью, `active = true`.
3. Жадно добавлять блоки, пока сумма по фазе не приблизится к целевой; **не повторять подряд тот же `slug`** (ротация вариантов).
4. Подгонка суммы к целевой в пределах `min_m`/`max_m`; мелкий остаток `< порога` (например 100 м) — **добор к последнему блоку** с поясняющей строкой в тексте, а не новая карточка.
5. Округление к шагу 25 м.

**Выход:** массив серий как сейчас для формы плавания: `{ distance, description }[]`.

Fallback: если каталог пуст или не хватает блоков — использовать существующий эвристический `generateSwimWorkoutPlan`.

## 6. Интеграция в приложение

| Компонент | Изменение |
|-----------|-----------|
| UI «Плавание» | Выбор цели из каталога целей + объём; кнопка «Сгенерировать» вызывает сборку из каталога с fallback. |
| Supabase | Миграция таблицы `swim_block_template` (+ при необходимости `swim_goal`). |
| Агент | Опционально позже: тулы `list_swim_blocks`, подбор блоков по запросу пользователя. |

---

## 7. Этапы внедрения

1. Зафиксировать JSON-пример одной записи блока + **10–15** начальных записей (SQL seed или скрипт).
2. Миграция + RLS + seed.
3. Импорт типовых серий из пользовательских данных в блоки (`own`).
4. Функция сборки `buildWorkoutFromCatalog(goalCode, volumeM)` и подключение к странице плавания.
5. Перенос лучших шаблонов из `generatePlan.ts` в таблицу; сузить роль чисто эвристического генератора до fallback.
